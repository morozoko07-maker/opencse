T-01

Basic definitions

基本定義
2–5 M

If you can define these seven words precisely and give one example each, you have already secured the easy marks in Module 1.

Data
Known facts that can be recorded and that have an implicit meaning. On its own, a number like 72 is not information; context gives it meaning.
Database
A collection of related data — logically coherent, built for a specific purpose, and representing some part of the real world.
Mini-world
The part of the real world that is represented in the database (e.g. students, courses and grades at a university). Changes in the mini-world are reflected in the database.
DBMS
Database Management System — a software package/system that facilitates defining, constructing, manipulating and sharing a database among many users and applications.
Database system
The DBMS software together with the data itself; applications are sometimes included. Not the same as the DBMS alone.
Metadata
Data about data: the description of the database's structures, data types, constraints and users, stored in the DBMS catalog / data dictionary.
Schema
The description of the database — its structure, types and constraints. Changes rarely.
Instance / state
The actual data stored at a particular moment. Changes whenever the database is updated.
Exam phrasing

“A database is an organised collection of related data that represents a mini-world; a DBMS is the software that defines, constructs, manipulates and shares it; a database system is the DBMS plus the data.” That single sentence answers most “define” questions.

Data vs information

Data are raw recorded facts; information is data processed into a form useful for decision-making. A database stores data; a query produces information.

The chain to remember

Mini-world → data → database → DBMS → database system → users. The database is a model of the mini-world, the schema is the model's blueprint, and the instance is its current snapshot.

T-03

Typical DBMS functionality

DBMSの機能
5 M

A DBMS is not a storage cupboard. It is the layer that turns shared data into a controlled, queryable, recoverable resource.

  1. Define the database — specify its data types, structures and constraints, and store that description in the catalog.
  2. Construct / load the initial contents onto secondary storage, often by converting existing files.
  3. Manipulate the data — retrieval (queries, reports) and modification (insert, delete, update), including access through web applications.
  4. Share the data among concurrent users and programs while keeping it valid and consistent.
  5. Protect the database — security against unauthorised access, plus backup and recovery.
  6. Maintain the database and programs over the application's lifetime — reorganising files, monitoring performance, evolving the schema.

Other features listed in the textbook: active processing (rules/triggers that take internal actions), presentation and visualisation of data, and support for multiple interfaces.

One-line answer

“A DBMS lets users define, construct, manipulate, share, protect and maintain a database, while hiding physical storage details and enforcing constraints.”

T-04

The UNIVERSITY example

大学データベース
2–5 M

The textbook's running example is a simplified university. It is useful because it shows how a conceptual model separates things from the links between them.

Entities

Things we store

STUDENT, COURSE, SECTION (a specific offering of a course), DEPARTMENT, INSTRUCTOR.

Relationships

How they connect

Sections are of courses; students take sections; courses have prerequisites; instructors teach sections; courses are offered by departments; students major in departments.

These entities and relationships are expressed in a conceptual data model — most commonly the ER model (Chapters 3–4), then mapped to relational tables (Chapter 5/9).

Why the example is exam-friendly

  • It contains a weak entity candidate: SECTION depends on COURSE.
  • It contains M:N relationships: STUDENT–SECTION (enrolment) and COURSE–PREREQUISITE (recursive).
  • It contains 1:N relationships: DEPARTMENT–INSTRUCTOR, COURSE–SECTION.
  • It shows a multi-valued attribute candidate: a student's previous degrees.
T-05

Main characteristics of the database approach

データベース手法の特徴
7 M · repeat

This is the single most likely 7-mark question in Module 1. Learn five headings, then one sentence of explanation and one benefit for each.

1. Self-describing nature of a database system

The DBMS catalog stores the description of the database — structures, data types and constraints. This description is metadata. Because the DBMS reads the catalog at runtime, the same software can work with many different databases; the catalog is what makes the system self-describing.

2. Insulation between programs and data

Called program–data independence. The structure of the data can change without rewriting the programs that access it. In file processing, every program hard-codes the record layout; in a DBMS, programs refer to the schema through the DBMS.

3. Data abstraction

A data model hides storage details and gives users a conceptual view. Programs refer to model constructs (tables, objects) rather than byte offsets, block addresses or file organisation.

4. Support of multiple views of the data

Each user or application can see a different view containing only the data of interest. A clerk sees customer names and balances; an analyst sees aggregates; neither needs the full schema.

5. Sharing of data and multi-user transaction processing

Many concurrent users can retrieve and update the same database. Concurrency control guarantees each transaction is correctly executed or aborted; the recovery subsystem ensures that every completed transaction's effect is permanent even after a failure.

6. OLTP as a major application class

Online transaction processing allows hundreds of concurrent transactions per second — banking, reservations, e-commerce — which is only safe because of the concurrency and recovery machinery above.

Memory hook

S-I-A-M-S — Self-describing, Insulation, Abstraction, Multiple views, Sharing. Then add OLTP as the sixth point if the question says “explain in detail”.

Don't confuse

These are characteristics of the database approach, not “features of SQL”. Keep DDL/DML for the languages question.

T-07

Advantages of the database approach

データベース手法の利点
7–10 M

The exam may ask for “advantages over file processing”. Start with the problems of file systems, then show how each DBMS property removes them.

Core advantages

  1. Controlling redundancy. Data is stored once and shared, instead of being duplicated in every application file. Less duplication means less inconsistency and less storage.
  2. Restricting unauthorised access. The DBMS enforces security and authorisation; users see only permitted data.
  3. Persistent storage for program objects. Object-oriented DBMSs can store complex objects persistently, beyond the life of the program.
  4. Storage structures for efficient query processing. Indexes, hash tables, clustering and query optimisation let the DBMS answer queries without scanning everything.
  5. Backup and recovery services. The DBMS can restore a consistent state after a crash or media failure.
  6. Multiple interfaces. Casual users, programmers, clerks and analysts can each use a suitable interface over the same data.
  7. Representing complex relationships. Many-to-many, recursive and multi-entity relationships are modelled and queried directly.
  8. Enforcing integrity constraints. Keys, referential integrity, domain and business rules are enforced centrally — not re-coded in every program.
  9. Drawing inferences and actions. Deductive and active rules (triggers) can derive facts or react to events.

Additional implications

  • Potential for enforcing standards — names, formats, screens, reports, metadata across the organisation.
  • Reduced application development time — each new application reuses the shared data and DBMS facilities.
  • Flexibility to change data structures — the schema can evolve as requirements change.
  • Availability of current information — crucial for reservation and transaction systems.
  • Economies of scale — consolidating data and applications avoids wasteful overlap between departments.
File-system contrast

Redundancy → inconsistency; program-data dependence → maintenance cost; no central control → poor security; no concurrency control → lost updates; no recovery → corruption. The database approach addresses each one.

T-08

When not to use a DBMS

DBMSが不要な場合
5 M

A DBMS is not automatically the right answer. The textbook gives three buckets: the costs, when it may be unnecessary, and when no DBMS may suffice.

Inhibitors / costs

  • High initial investment in software, hardware, training and conversion.
  • Overhead for generality — security, concurrency control, recovery and integrity checks cost time and resources.

When a DBMS may be unnecessary

  • The database and applications are simple, well defined and not expected to change.
  • There are stringent real-time requirements that the DBMS overhead would violate.
  • Multiple-user access is not required — a single-user embedded file may be enough.

When no DBMS may suffice

  • The system cannot handle the complexity of the data because of modelling limitations.
  • Users need special operations that the DBMS does not support.
Balance your answer

If asked “advantages and disadvantages”, give the advantages first, then these costs and conditions. A one-sided answer caps at about half marks.

T-10

Data models & their categories

データモデル
5 M

A data model is a set of concepts for describing structure, operations and constraints — a vocabulary plus rules for using it.

Three components

Structure
Constructs that define the database: elements and their data types, groups such as entities/records/tables, and relationships among groups.
Operations
Basic operations (generic insert, delete, update) and user-defined operations (e.g. compute_student_gpa, update_inventory) used for retrieval and change.
Constraints
Restrictions on valid data that must hold at all times (keys, domains, cardinality rules, business rules).
CategoryLevelPurpose / examples
Conceptual (high-level, semantic)Close to how users perceive dataEntity-based/object-based models: ER model, UML class diagrams. Used for conceptual schema design.
Physical (low-level, internal)How data is stored in the computerFile organisations, record formats, indexes, access paths. Usually specified in DBMS manuals rather than a formal model.
Implementation (representational)Between the twoConcepts understood by users but implementable: relational, network, hierarchical, object-relational. Used by commercial DBMSs.
Order of use

Conceptual (ER) → implementation (relational tables) → physical (files/indexes). The three-schema architecture mirrors this progression.

T-12

Three-schema architecture

三層スキーマ構造
7–10 M · repeat

The architecture exists to deliver two things: program–data independence and multiple user views. Learn the three levels and the two mappings — the diagram is worth marks.

The three levels

Internal schema
Describes physical storage structures and access paths — files, pages, indexes, hashing. Typically uses a physical data model. One per database.
Conceptual schema
Describes the structure and constraints of the whole database for the user community, hiding physical details. Uses a conceptual or implementation model (usually relational). One per database.
External schemas
Describe the various user views, each showing only relevant data. Usually use the same data model as the conceptual schema. Many per database.

Mappings

  • External/conceptual mapping — defines how each external view is derived from the conceptual schema. This is what gives logical data independence.
  • Conceptual/internal mapping — defines how conceptual constructs are stored physically. This is what gives physical data independence.

Programs refer to an external schema; the DBMS maps the request down to the internal schema for execution, then reformats the extracted data to match the user's external view (e.g. an SQL result rendered on a web page).

Important caveat

The three-schema architecture is not explicitly implemented in most commercial DBMS products, but it is the standard way to explain database organisation and data independence.

Drawing marks

Draw three horizontal layers, label many external schemas, one conceptual schema, one internal schema, and both mappings. Add “views / tables / files” beside the layers.

T-13

Data independence

データ独立性
5–7 M

Data independence is the capacity to change one schema level without changing the level above it. The mappings absorb the change.

Logical

Logical data independence

Change the conceptual schema without changing external schemas or application programs. Example: add a new column or split a table; existing views and programs still work because the external/conceptual mapping is adjusted.

Physical

Physical data independence

Change the internal schema without changing the conceptual schema. Example: create a new index, change file organisation or move data to another disk; the logical design and queries stay the same.

Program–data independence

The broader property: application programs are insulated from changes in data structure and storage organisation. In file systems, programs depend on the exact record layout; in a DBMS they depend on the schema and let the DBMS handle storage.

Change madeLevel changedIndependence type that protects the level above
Add an index or reorganise filesInternalPhysical
Add an attribute or restructure tablesConceptualLogical
Change a view definitionExternalAffects only that view's users
Key sentence

When a lower-level schema changes, only the mapping to the higher level must be updated; the higher-level schema and application programs remain unchanged.

T-14

DBMS languages

データベース言語
5–7 M · repeat

DDL — Data Definition Language

Used by the DBA and designers to specify the conceptual schema. In many DBMSs it also defines internal and external schemas. Examples: CREATE TABLE, ALTER TABLE, DROP TABLE.

SDL — Storage Definition Language

Defines the internal schema — file organisation, indexes, storage parameters. In modern systems these are usually DBMS commands or parameters rather than a separate language.

VDL — View Definition Language

Defines external schemas / user views. In relational systems, SQL's CREATE VIEW serves this purpose.

DML — Data Manipulation Language

Specifies retrievals and updates. It can be embedded in a host language (COBOL, C, C++, Java) or used stand-alone as a query language.

High-level / non-proceduralLow-level / procedural
Also calledDeclarative, set-orientedRecord-at-a-time, navigational
You specifyWhat data to retrieveHow to retrieve it, record by record
ConstructsSQL SELECT, set operationsLoops, pointers, navigation (FIND, GET)
OptimisationDBMS can optimise the planProgrammer largely controls the path

Embedded vs stand-alone

  • Embedded DML — SQL statements inside a host program (embedded SQL, SQLJ), compiled with the application.
  • Stand-alone DML — commands typed directly at an interactive interface; this is what we usually call a query language.
Beyond the textbook

Modern SQL is often divided into DDL, DML, DCL (GRANT/REVOKE) and TCL (COMMIT/ROLLBACK). The syllabus focuses on DDL and DML, but the paper also tests privileges and triggers.

T-17

DBMS component modules

DBMSの構成要素
5–7 M

The textbook's module diagram separates query processing from storage management. You do not need every arrow, but name the modules and say what each does.

Front end

Query processing

  • DDL compiler — processes schema definitions, stores descriptions in the catalog.
  • Query compiler / parser — checks syntax, builds a parse tree.
  • Query optimiser — chooses an execution plan with least estimated cost.
  • Runtime database processor — executes the plan, performs updates and constraint checks.
Back end

Storage manager

  • File manager — allocates disk space, manages file structures.
  • Buffer manager — loads pages into memory and decides what to evict.
  • Index manager — maintains indexes for fast search.
  • Data dictionary / catalog — metadata for all modules.

Other modules

Authorisation/security manager, recovery manager, concurrency-control manager, transaction manager, and the utilities listed earlier. In a client–server system the query-processing front end may sit on clients and storage management on the server.

T-18

Centralized & client–server architectures

システム構成
5–7 M

Centralized

DBMS software, hardware, application programs and user-interface processing all run on one system. Users may connect through remote terminals, but all processing happens at the central site. Simple to manage; a single point of failure and a scalability bottleneck.

Two-tier client–server

Specialised servers (file, print, DBMS, web, email) and clients connected over a network. The client provides the user interface and application logic; the DBMS server provides query and transaction services. Relational DBMS servers are often called SQL servers, query servers or transaction servers.

Clients use an API — ODBC (Open Database Connectivity) or JDBC (Java) — to talk to the server. A client can connect to several data sources.

Three-tier

An intermediate application server / web server holds the business logic and web connectivity. The client talks to the middle tier; the middle tier talks to the database server.

2-tier3-tier
LayersClient + DB serverClient + application server + DB server
Business logicOften on the clientOn the middle tier
SecurityClients may reach DB directlyDB only reachable via middle tier
Typical useLAN applicationsWeb applications
Why three tiers

The middle tier acts as a conduit, sending partially processed data between server and client, and enhances security because clients cannot directly access the database server.

T-20

Steps in query processing

問い合わせ処理
7–10 M · paper

This appeared as a 10-mark question in the CIE-I paper. The answer is a pipeline, not a list of random modules.

  1. User query input. The user writes an SQL query at an interface (or an application submits it).
  2. Parser. Checks syntax and grammar, converts the query into a parse tree. If the syntax is wrong, an error is returned.
  3. Translator / query compiler. Converts the SQL into an internal representation, typically relational algebra.
  4. Query optimiser. Enumerates execution plans and picks the one with the lowest estimated cost in time, memory and CPU. Example: choose an index scan instead of a full table scan.
  5. Execution engine. Executes the chosen plan, interacting with the storage system to fetch and update data.
  6. Storage manager. Handles storage and retrieval through the file manager (disk structures), buffer manager (memory pages) and index manager (fast search).
  7. Database. The actual data — tables, indexes, catalog — stored on secondary storage. Results are returned to the user.
Mark allocation (from the paper)

Flow explanation ≈ 5 marks · diagram ≈ 5 marks. Draw the pipeline and label parser → translator → optimiser → execution → storage manager → database.

T-21

Database design process

データベース設計
5 M

Database design has two main activities: database design (the schema) and applications design (the programs and interfaces that access it). Chapter 3 focuses on the conceptual schema.

  1. Requirements collection and analysis. Interview users, study documents, identify data needs and operations. Output: a requirements specification.
  2. Conceptual design. Build a high-level, DBMS-independent model — usually an ER diagram — of entities, attributes, relationships and constraints.
  3. Logical design. Map the conceptual model to an implementation model — usually relational tables, keys and foreign keys.
  4. Physical design. Choose file organisations, indexes, storage parameters and access paths for the expected workload.
  5. Application design. Design transactions, screens, reports and program interfaces; implement and test.
Why ER first

The ER model is closer to how users think, so it is easier to validate requirements before committing to tables. Mapping to relational comes later.

T-22

The COMPANY requirements

企業データベース

Departments

  • The company is organised into DEPARTMENTs, each with a unique name and number.
  • Each department has one employee who manages it; we record the manager's start date.
  • A department may have several locations (multi-valued attribute).
  • Each department controls a number of PROJECTs.

Projects

  • Each project has a unique name, a unique number, and a single location.

Employees

  • We store SSN, address, salary, sex and birth date.
  • Each employee works for exactly one department but may work on several projects.
  • For each project we record the hours per week the employee works on it.
  • We record each employee's direct supervisor (recursive relationship).

Dependents

  • Each employee may have several DEPENDENTs.
  • For each dependent: name, gender, birth date and relationship to the employee.
Design decisions hiding here

“Several locations” → multivalued attribute / separate table. “Manager” → 1:1 MANAGES with MgrStartDate. “Works on several projects + hours” → M:N WORKS_ON with a relationship attribute. “Dependents” → weak entity. “Supervisor” → recursive 1:N.

Keys & identifiers

キー属性
2–5 M
Key attribute
An attribute whose value is unique for each entity of that type — SSN for EMPLOYEE. In an ER diagram it is underlined.
Composite key
A key made of several attributes — VehicleTagNumber(Number, State) for CAR.
Superkey
Any set of attributes that uniquely identifies an entity. Every key is a superkey, but not every superkey is minimal.
Candidate key
A minimal superkey — no attribute can be removed without losing uniqueness. An entity type may have several.

The candidate key chosen by the designer to identify entities; underlined in the ER diagram and declared PRIMARY KEY in SQL.

An attribute that distinguishes entities of a weak entity only within the owner — e.g. dependent Name. Shown with a dashed underline; also called a discriminator.

Superkey ⊇ candidate key → chosen one becomes primary key. Minimality is what separates a candidate key from a mere superkey.

Cardinality ratio — maximum participation

Participation constraint — minimum participation

  • Total participation (existence dependency): every entity of the type must participate. Drawn with a double line. Example: every DEPARTMENT must have a manager.
  • Partial participation: some entities may not participate. Drawn with a single line. Example: not every employee manages a department.

(min, max) notation

On each edge, write the minimum and maximum number of relationship instances in which an entity may participate. Default with no constraint: (0, n). Always min ≤ max, min ≥ 0, max ≥ 1. Read the pair next to the entity, looking away from that entity.

RelationshipEMPLOYEE sideOther sideReading
MANAGES(0,1)DEPARTMENT (1,1)An employee manages at most one department; every department has exactly one manager.

Reading trick

Stand on the entity and look across the line: “How many times can I appear in this relationship?” The pair sits on your side. For MANAGES standing on DEPARTMENT: every department appears exactly once → (1,1).

Cardinality ≠ participation

Cardinality is the maximum (1, N, M). Participation is the minimum (0 = partial, 1 = total). A relationship can be 1:N in cardinality and total on the N side.

T-28

Weak entity types

弱実体
5–7 M · repeat

A weak entity has no key of its own. It borrows identity from an owner through an identifying relationship.

Weak entity type
An entity type that does not have a key attribute of its own. It must participate totally in an identifying relationship with an owner/identifying entity type.
Partial key
An attribute that uniquely identifies weak entities only within the owner. Also called a discriminator. Shown with a dashed underline.
Identifying relationship
The relationship through which the weak entity is identified by its owner. Shown as a double diamond.

Identity rule

The weak entity is identified by the combination of:

  • its partial key, and
  • the particular owner entity it is related to through the identifying relationship.

COMPANY example: DEPENDENT

  • A dependent is identified by their first name plus the employee they belong to.
  • Name is the partial key (dashed underline).
  • DEPENDENT is the weak entity type; EMPLOYEE is the identifying owner.
  • DEPENDENTS_OF is the identifying relationship (double diamond).
  • DEPENDENT always has total participation: a dependent cannot exist without an employee.

In notation: weak entity = double rectangle; identifying relationship = double diamond; partial key = dashed underline.

Why not a strong entity?

The name “Alice” is not unique across the company, but it may be unique among one employee's dependents. So the full identifier is (Essn, Name) — owner key plus partial key.

T-31

Ternary & n-ary relationships

三項関連
5 M
  • Binary = degree 2 (most COMPANY relationships).
  • Ternary = degree 3; n-ary = degree n.
  • A relationship of degree n is not, in general, equivalent to n binary relationships — the binaries can express different information.
  • Constraints are harder to specify for n > 2; both (min,max) and a 1/M/N marker may be needed on an edge.

Classic example: SUPPLY

SUPPLY relates SUPPLIER, PART and PROJECT: “Supplier S supplies part P to project J in quantity Q.” The quantity is a property of the triple, not of any pair. Three binary relationships (supplies part, supplies project, uses part) cannot represent which supplier supplied which part to which project.

Redundancy rule

If a binary relationship can always be derived from a higher-degree relationship, it is redundant. Example: TAUGHT_DURING can be derived from the ternary OFFERS, so keeping both may be unnecessary.

Exam line

“An n-ary relationship is used when an association has meaning only for the combination of n entities; it cannot generally be decomposed into binary relationships without losing information.”

T-33

ER → relational mapping

関係モデルへの変換
7–10 M · high yield

The exam may not label it “mapping”, but every request to “give the relational schema” is this algorithm. Learn the seven rules.

  1. Strong entity type → relation. Include all simple attributes; flatten composite attributes into their components; choose one key as primary key.
  2. Weak entity type → relation. Include its attributes plus the owner's primary key as a foreign key. Primary key = owner key + partial key. Use ON DELETE CASCADE.
  3. 1:1 relationship. Add the primary key of one side as a foreign key in the other — preferably the side with total participation. Add UNIQUE to enforce one-to-one.
  4. 1:N relationship. Add the primary key of the “1” side as a foreign key on the “N” side. Do not create a new table.
  5. M:N relationship. Create a new relation containing the primary keys of both sides (as foreign keys) plus any relationship attributes. The primary key is the combination of both keys.
  6. Multi-valued attribute. Create a separate relation with the owner's primary key plus the attribute; primary key is the combination.
  7. n-ary relationship. Create a new relation with the primary keys of all participating entity types plus relationship attributes.

Applied to COMPANY

  PK SSN · FK SuperSSN → EMPLOYEE(SSN) · FK Dno → DEPARTMENT(Dno)

  PK Dno · FK MgrSSN → EMPLOYEE(SSN)

  PK (Dno, Dlocation) · FK Dno → DEPARTMENT(Dno)

  PK Pno · FK Dno → DEPARTMENT(Dno)

T-01

SQL — what it is

SQLの概要
2–5 M

SQL is a declarative, set-oriented language: you state the result you want, and the DBMS decides how to compute it.

  • Originally developed at IBM (SEQUEL, early 1970s); standardised as SQL-86/89, SQL-92, SQL-99 (SQL3), then further revisions.
  • The standard language for relational DBMSs; also the basis for object-relational features.
  • Non-procedural — one statement can process a whole set of rows; no loops or pointers required.
  • Can be used stand-alone (interactive) or embedded in a host language (C, C++, Java) or a procedural extension (PL/SQL, T-SQL).
  • SQL includes DDL, DML, view definition, constraint definition, transaction control (COMMIT/ROLLBACK), authorisation (GRANT/REVOKE) and, in extensions, triggers.

DDLDefine/modify schemaCREATE, ALTER, DROP, TRUNCATE
DMLManipulate dataSELECT, INSERT, UPDATE, DELETE

TCLControl transactionsCOMMIT, ROLLBACK, SAVEPOINT
Naming note

SQL keywords are case-insensitive; identifiers depend on the DBMS. Put string literals in single quotes ('Smith'), not double quotes — double quotes usually mean an identifier.

CHAR vs VARCHAR

CHAR(10) always stores 10 characters and pads with spaces; VARCHAR(10) stores only the characters supplied (plus a length). Use CHAR for fixed codes, VARCHAR for names and addresses. VARCHAR2 is Oracle's variable-length string with Oracle-specific NULL/empty-string semantics.

Date literals

Standard: DATE '1955-01-09'. Oracle accepts TO_DATE('09-JAN-1955','DD-MON-YYYY') and is sensitive to NLS_DATE_FORMAT. The sample paper's Bdate LIKE '195%' works when the date is compared as a string (implicit conversion) — be ready to explain the safer range predicate.

A constraint is a rule the DBMS enforces on every change. Declare it once; every program inherits it.

Column-level vs table-level

A constraint on a single column can be written after the type. A constraint involving several columns must be a table constraint:

SQL · composite key
CREATE TABLE WORKS_ON (
  SSN    CHAR(9),
  Pno    INT,
  Hours  DECIMAL(4,1),
  PRIMARY KEY (SSN, Pno),          -- table constraint
  FOREIGN KEY (SSN) REFERENCES EMPLOYEE(SSN),
  FOREIGN KEY (Pno) REFERENCES PROJECT(Pno)
);

Referential actions

ActionWhen the parent row is deleted/updated
ON DELETE CASCADEDelete the child rows too (e.g. delete an employee → delete their dependents).
ON DELETE SET NULLSet the child's foreign key to NULL (column must allow NULL).
ON DELETE SET DEFAULTSet the child's foreign key to its default value.
ON DELETE RESTRICT / NO ACTIONRefuse the delete if children exist (the safe default in many systems).

Named constraints

Name a constraint so you can drop or diagnose it later: CONSTRAINT fk_emp_dept FOREIGN KEY (Dno) REFERENCES DEPARTMENT(Dno). Then ALTER TABLE EMPLOYEE DROP CONSTRAINT fk_emp_dept;.

What CHECK cannot do

A CHECK constraint is evaluated on one row (plus constants); it cannot query another table or count rows. Cross-table rules need an assertion (standard SQL, rarely implemented) or a trigger.

Assertions vs triggers vs constraints

Use a constraint when the rule is local and declarative (key, domain, referential). Use a trigger when the rule needs queries, multiple rows, or side effects. Use an assertion when the standard supports it and the rule is a pure boolean condition over the database.

-- explicit column list (safest)
INSERT INTO EMPLOYEE (SSN, Name, Address, Gender, Salary, SuperSSN, Dno)
VALUES ('123456789', 'John Smith', '731 Fondren, Houston, TX', 'M', 30000, NULL, 5);

-- all columns, in table order
INSERT INTO DEPARTMENT
VALUES (5, 'Research', '333445555', DATE '1988-05-22');

-- multiple rows (standard / MySQL / PostgreSQL)
INSERT INTO PROJECT (Pno, Pname, Plocation, Dno) VALUES
  (1, 'ProductX', 'Bellaire', 5),
  (2, 'ProductY', 'Sugarland', 5),
  (3, 'ProductZ', 'Houston', 5);

-- copy rows from another table
INSERT INTO EMPLOYEE_ARCHIVE (SSN, Name, Salary)
SELECT SSN, Name, Salary FROM EMPLOYEE WHERE Dno = 5;

Rules

  • String and date literals need quotes; numbers do not.
  • Columns omitted from the list receive their DEFAULT or NULL. If a column is NOT NULL with no default, the insert fails.
  • The column list can be in any order, but the values must match that order.
  • A failed multi-row insert may leave earlier rows inserted unless the whole statement is in a transaction — use ROLLBACK to undo.
  • INSERT ... SELECT must produce matching number and compatible types of columns.
Rollback demo (lab)

Insert three rows, run SELECT * FROM Employee;, then ROLLBACK; and select again. The rows disappear because the insert was not committed. If autocommit is on, the rollback has nothing to undo — that is the point of the experiment.

T-07

UPDATE

データ更新
3–5 M · lab
SQL · updating rows
-- raise salary by 10% for department 5
UPDATE EMPLOYEE
SET Salary = Salary * 1.10
WHERE Dno = 5;

-- update several columns at once
UPDATE EMPLOYEE
SET Address = 'Houston, TX', Salary = 35000
WHERE SSN = '123456789';

-- update with a subquery: set everyone to the company average
UPDATE EMPLOYEE
SET Salary = (SELECT AVG(Salary) FROM EMPLOYEE)
WHERE Dno = 5;

-- update all rows (dangerous without WHERE)
UPDATE EMPLOYEE SET Salary = Salary + 5000;

-- update a job title (lab experiment)
UPDATE Employee SET Job = 'Senior Analyst' WHERE Empno = 101;

Rules and hazards

  • Always write the WHERE clause first, then the SET values. A missing WHERE updates every row.
  • The SET expressions see the old values of the row (standard behaviour), so Salary = Salary * 1.1 is well defined.
  • Updates must satisfy all constraints; one violating row aborts the statement (or the transaction).
  • A subquery in SET must return a single value per row.
  • Use a transaction (BEGIN … COMMIT/ROLLBACK) for bulk updates so you can undo a mistake.
T-08

DELETE

データ削除
3–5 M · lab
SQL · deleting rows
-- delete one employee
DELETE FROM EMPLOYEE WHERE SSN = '123456789';

-- delete by condition
DELETE FROM EMPLOYEE WHERE Dno = 5 AND Salary < 30000;

-- delete using a subquery
DELETE FROM WORKS_ON
WHERE Pno IN (SELECT Pno FROM PROJECT WHERE Dno = 5);

-- delete all rows (table remains)

-- remove all rows quickly (DDL; usually cannot roll back)

Referential integrity on delete

If a deleted row is referenced by child rows, the DBMS applies the foreign key's action: CASCADE deletes children, SET NULL nulls the reference, or RESTRICT/NO ACTION refuses the delete. Deleting an employee with dependents therefore either deletes the dependents (if cascaded) or fails (if restricted).

Exam distinction

DELETE FROM T; is DML and can be rolled back. TRUNCATE TABLE T; is DDL, resets storage and usually cannot be rolled back. DROP TABLE T; removes the table itself.

T-09

SELECT — the basic form

基本検索
5–10 M · core
SQL · skeleton
SELECT   [DISTINCT] select_list
FROM     table_list
[WHERE   row_condition]
[GROUP BY grouping_columns]
[HAVING  group_condition]
[ORDER BY sort_columns [ASC|DESC]]
[LIMIT n [OFFSET m]];        -- MySQL/PostgreSQL; Oracle: FETCH FIRST n ROWS ONLY

Examples

SQL · COMPANY
-- all columns, all rows
SELECT * FROM EMPLOYEE;

-- projection: only some columns
SELECT Name, Salary FROM EMPLOYEE;

-- rename output columns
SELECT Name AS Employee_Name, Salary * 12 AS Annual_Salary
FROM EMPLOYEE;

-- remove duplicate values
SELECT DISTINCT Dno FROM EMPLOYEE;

-- filter rows
SELECT Name, Salary FROM EMPLOYEE
WHERE Dno = 5 AND Salary > 30000;

-- sort
SELECT Name, Salary FROM EMPLOYEE
ORDER BY Salary DESC, Name ASC;

-- top 3 salaries (MySQL/PostgreSQL)
SELECT Name, Salary FROM EMPLOYEE
ORDER BY Salary DESC
LIMIT 3;

Logical order of evaluation

SQL is written SELECT first but evaluated in this order:

  1. FROM — form the working table (joins happen here).
  2. WHERE — filter individual rows.
  3. GROUP BY — form groups.
  4. HAVING — filter groups.
  5. SELECT — compute the output expressions and aliases.
  6. DISTINCT — remove duplicate result rows.
  7. ORDER BY — sort the final rows.
  8. LIMIT/OFFSET — cut the result.
Why this order matters

You cannot use a SELECT alias in WHERE (it does not exist yet), but you can use it in ORDER BY. Aggregates are not allowed in WHERE — that is what HAVING is for.

SELECT * — use with care

SELECT * is fine for exploration and for “display all details” questions. In production it is fragile: adding a column changes the result shape, and it fetches data you may not need.

The paper's salary question

SQL · salary aggregates
SELECT SUM(Salary) AS Total_Salary,
       MAX(Salary) AS Max_Salary,
       MIN(Salary) AS Min_Salary,
       AVG(Salary) AS Avg_Salary
FROM EMPLOYEE;

Without GROUP BY this returns exactly one row, even if EMPLOYEE is empty: COUNT(*) would be 0 and the others NULL.

Counts

SQL · counting
SELECT COUNT(*) AS Employees FROM EMPLOYEE;

SELECT COUNT(DISTINCT Dno) AS Departments_With_Staff FROM EMPLOYEE;

SELECT COUNT(SuperSSN) AS Employees_With_Supervisor FROM EMPLOYEE;
-- differs from COUNT(*): the top boss has NULL SuperSSN

SELECT COUNT(*) AS Employees_On_Projects
FROM WORKS_ON;   -- counts assignments, not distinct employees
COUNT question trap

“How many employees work on projects?” → COUNT(DISTINCT SSN) from WORKS_ON, because one employee may appear on several projects. COUNT(*) would count assignments.

AVG and NULL

If salaries are 10000, 20000 and NULL, AVG(Salary) = 15000 (divides by 2), not 10000. Use AVG(COALESCE(Salary,0)) if NULL should count as zero — and say why.

T-12

GROUP BY & HAVING

グループ化
7–10 M · paper

Rules

  • Every expression in the SELECT list must be either an aggregate or a column listed in GROUP BY.
  • WHERE filters rows before grouping; HAVING filters groups after grouping. Aggregates cannot appear in WHERE.
  • A GROUP BY column can be omitted from SELECT; the result then has repeated-looking rows that are actually distinct groups.
  • NULLs form their own group.
  • Some DBMSs (MySQL with relaxed mode, PostgreSQL with functional dependency) allow selecting other columns when grouping by a primary key; Oracle is strict. In an exam, list all non-aggregate columns.

Per-department statistics

SQL · group by department
SELECT Dno,
       COUNT(*)       AS No_of_Employees,
       AVG(Salary)    AS Avg_Salary,
       MAX(Salary)    AS Max_Salary
FROM EMPLOYEE
GROUP BY Dno
ORDER BY Dno;

Only groups that satisfy a condition

SQL · HAVING
-- departments with more than 2 employees
SELECT Dno, COUNT(*) AS No_of_Employees
FROM EMPLOYEE
GROUP BY Dno
HAVING COUNT(*) > 2;

-- departments whose average salary exceeds 40000
SELECT Dno, AVG(Salary) AS Avg_Salary
FROM EMPLOYEE
GROUP BY Dno
HAVING AVG(Salary) > 40000;

-- employees working on more than 3 projects (paper)
SELECT E.SSN, E.Name, COUNT(W.Pno) AS Project_Count
FROM EMPLOYEE E
JOIN WORKS_ON W ON E.SSN = W.SSN
GROUP BY E.SSN, E.Name
HAVING COUNT(W.Pno) > 3;
Paper variant

The CIE-I solution groups by every EMPLOYEE column because it selects E.*. That is valid in Oracle, but wordy. The exam-safe minimum is to group by the primary key plus every other selected non-aggregate column.

WHERE vs HAVING

WHEREHAVING
Operates onIndividual rowsGroups

AggregatesNot allowedAllowed (and typical)
ExampleWHERE Dno = 5HAVING COUNT(*) > 2

If a condition can go in either place, put it in WHERE — it reduces rows earlier and is usually faster.

T-14

Subqueries & nested queries

副問い合わせ
7–10 M · paper

A subquery is a SELECT inside another statement. The exam loves “employees who…”, “departments with…”, and “projects involving Smith” — all subquery shapes.

Kinds

  • Scalar subquery — returns one value; usable with =, <, >.
  • Row/table subquery — returns a list or table; used with IN, ANY, ALL, EXISTS.
  • Uncorrelated — independent of the outer query; evaluated once.
  • Correlated — references the outer row (e.g. E.SSN); conceptually evaluated per outer row.

Comparison with an aggregate

SQL · above average
SELECT Name, Salary
FROM EMPLOYEE
WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEE);

IN — Smith's projects (paper)

SQL · nested IN
SELECT Pno
FROM PROJECT
WHERE Dno IN (
  SELECT Dno FROM DEPARTMENT
  WHERE MgrSSN IN (
    SELECT SSN FROM EMPLOYEE WHERE Name = 'Smith'
  )
)
OR Pno IN (
  SELECT Pno FROM WORKS_ON
  WHERE SSN IN (
    SELECT SSN FROM EMPLOYEE WHERE Name = 'Smith'
  )
);

This answers “projects controlled by a department managed by Smith, or projects Smith works on”. Read the OR carefully — it is two different routes to the same project list.

EXISTS / NOT EXISTS

SQL · no dependents (paper)
SELECT E.Name
FROM EMPLOYEE E
WHERE NOT EXISTS (
  SELECT 1
  FROM DEPENDENT D
  WHERE D.Essn = E.SSN
);

“More than 3 projects” with a correlated count

SQL · correlated subquery
SELECT E.SSN, E.Name
FROM EMPLOYEE E
WHERE (SELECT COUNT(*) FROM WORKS_ON W WHERE W.SSN = E.SSN) > 3;

Second-highest salary

SQL · nested max
SELECT MAX(Salary) AS Second_Highest
FROM EMPLOYEE
WHERE Salary < (SELECT MAX(Salary) FROM EMPLOYEE);

Top-N alternative: SELECT DISTINCT Salary FROM EMPLOYEE ORDER BY Salary DESC LIMIT 1 OFFSET 1; (MySQL/PostgreSQL). Oracle: use FETCH FIRST 1 ROW ONLY with an offset, or DENSE_RANK().

Division — employees who work on every project in department 5

SQL · double NOT EXISTS
SELECT E.Name
FROM EMPLOYEE E
WHERE NOT EXISTS (
  SELECT 1
  FROM PROJECT P
  WHERE P.Dno = 5
    AND NOT EXISTS (
      SELECT 1 FROM WORKS_ON W
      WHERE W.SSN = E.SSN AND W.Pno = P.Pno
    )
);

Read it as: “there is no project in department 5 that this employee does not work on.” This double-NOT EXISTS pattern is the standard way to write relational division and is worth memorising.

Department with the highest average salary

SQL · compare to all averages
SELECT Dno, AVG(Salary) AS Avg_Salary
FROM EMPLOYEE
GROUP BY Dno
HAVING AVG(Salary) >= ALL (
  SELECT AVG(Salary) FROM EMPLOYEE GROUP BY Dno
);
NOT IN + NULL

WHERE x NOT IN (SELECT y …) returns no rows if the subquery produces a NULL, because x <> NULL is UNKNOWN. Prefer NOT EXISTS for “does not exist” questions.

EXISTS vs IN

IN compares values; EXISTS tests whether a row exists. EXISTS is null-safe and usually the better answer for correlated “has/has no” questions.

T-16

Views

ビュー
5–7 M · repeat

A view is a named stored query — a virtual table. It contains no data of its own (unless materialised); it derives rows from base tables each time it is used.

SQL · views
CREATE VIEW HighSalary AS
SELECT SSN, Name, Salary, Dno
FROM EMPLOYEE
WHERE Salary > 50000;

SELECT * FROM HighSalary WHERE Dno = 5;

-- department totals
CREATE VIEW DeptStats (Dno, EmpCount, AvgSalary) AS
SELECT Dno, COUNT(*), AVG(Salary)
FROM EMPLOYEE
GROUP BY Dno;

-- replace and drop
CREATE OR REPLACE VIEW HighSalary AS
SELECT SSN, Name, Salary, Dno FROM EMPLOYEE WHERE Salary > 60000;

DROP VIEW HighSalary;

Why use a view?

  • Security — expose only some columns/rows (hide Salary or other departments).
  • Simplicity — package a complex join/aggregation as one table-like object.
  • Logical data independence — applications use the view while base tables are restructured.
  • Customised presentation — different users see different views of the same data.
  • Consistency — one definition of a derived concept (e.g. “active employee”).

Updatable views

A view is generally updatable if it is derived from one base table, contains the primary key, and has no DISTINCT, GROUP BY, aggregate, UNION, or computed columns. Updates through the view are translated to the base table.

WITH CHECK OPTION prevents inserting/updating rows that would fall outside the view's WHERE:

SQL · check option
CREATE VIEW Dept5 AS
SELECT * FROM EMPLOYEE WHERE Dno = 5
WITH CHECK OPTION;

-- allowed: inserts a row with Dno = 5
-- rejected: inserts a row with Dno = 4 through this view

Materialized view

Stores the query result physically. Fast to read, but must be refreshed when base data changes. Used for expensive aggregates and data warehousing. Oracle: CREATE MATERIALIZED VIEW …; PostgreSQL similar.

View vs table

A table stores data; a view stores a definition. Dropping a view does not drop base data. A view can become invalid if a base table/column is dropped.

T-17

Assertions

表明
7–10 M · paper

An assertion is a schema-level boolean condition that the database must always satisfy. Unlike a CHECK constraint, it can query multiple tables and aggregate rows.

Syntax

SQL · standard
CREATE ASSERTION assertion_name
CHECK ( condition );

DROP ASSERTION assertion_name;

The condition must evaluate to TRUE for every valid state. The usual pattern is NOT EXISTS ( … bad situation … ).

Paper example — manager earns more than subordinates

SQL · CIE-I solution
CREATE ASSERTION Manager_Salary_Check
CHECK (
  NOT EXISTS (
    SELECT *
    FROM EMPLOYEE E, DEPARTMENT D
    WHERE E.Dno = D.Dno
      AND D.MgrSSN = E.SuperSSN
      AND E.Salary >= (
        SELECT Salary FROM EMPLOYEE
        WHERE SSN = D.MgrSSN
      )
  )
);

Reading it: find a pair (employee, department) where the employee works in that department, is directly supervised by its manager, and earns at least the manager's salary. If no such pair exists, the assertion holds.

Cleaner variants

SQL · other assertions
-- every department must have a manager
CREATE ASSERTION Every_Dept_Has_Manager
CHECK (NOT EXISTS (
  SELECT * FROM DEPARTMENT WHERE MgrSSN IS NULL
));

-- no employee may be assigned more than 40 hours total
CREATE ASSERTION Max_Weekly_Hours
CHECK (NOT EXISTS (
  SELECT SSN FROM WORKS_ON
  GROUP BY SSN
  HAVING SUM(Hours) > 40
));

-- salary of an employee cannot exceed their manager's
CREATE ASSERTION Salary_Below_Manager
CHECK (NOT EXISTS (
  SELECT * FROM EMPLOYEE E, EMPLOYEE M
  WHERE E.SuperSSN = M.SSN AND E.Salary > M.Salary
));
Reality check

Standard SQL defines assertions, but many commercial DBMSs — including Oracle — do not support CREATE ASSERTION. In practice the same rule is implemented with a trigger. Write the assertion for the exam, then add the trigger as the practical alternative.

Assertion vs CHECK

CHECK is attached to a table/column and sees one row; ASSERTION is attached to the schema and can see the whole database. That is the one-line answer.

T-18

Triggers

トリガー
7–10 M · paper

A trigger is a procedure that fires automatically when a specified event occurs on a table or view. It is the practical tool for complex integrity rules, auditing and derived data.

Anatomy

PartOptionsMeaning
TimingBEFORE / AFTER / INSTEAD OFBefore the change, after it, or instead of it (for views).

The paper's salary audit trigger

Oracle PL/SQL · CIE-I solution
CREATE OR REPLACE TRIGGER salary_audit
AFTER INSERT OR UPDATE OR DELETE ON EMPLOYEE
FOR EACH ROW
BEGIN
  IF INSERTING THEN
     DBMS_OUTPUT.PUT_LINE('New Salary: ' || :NEW.Salary);

  ELSIF UPDATING THEN
     DBMS_OUTPUT.PUT_LINE('Old Salary: ' || :OLD.Salary);
     DBMS_OUTPUT.PUT_LINE('New Salary: ' || :NEW.Salary);
     DBMS_OUTPUT.PUT_LINE('Difference: ' || (:NEW.Salary - :OLD.Salary));

  ELSIF DELETING THEN
     DBMS_OUTPUT.PUT_LINE('Deleted Salary: ' || :OLD.Salary);
  END IF;
END;
/

Explanation to write: row-level trigger → executes for each affected row. :OLD holds the value before the change; :NEW holds the value after. INSERT has only NEW; DELETE has only OLD; UPDATE has both. The trigger handles all three events with INSERTING/UPDATING/DELETING.

Prevent a salary decrease

Oracle PL/SQL · validation trigger
CREATE OR REPLACE TRIGGER prevent_salary_decrease
BEFORE UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
WHEN (NEW.Salary < OLD.Salary)
BEGIN
  RAISE_APPLICATION_ERROR(-20001, 'Salary cannot be decreased');
END;
/

Maintain a derived column

Oracle PL/SQL · derived value
CREATE OR REPLACE TRIGGER set_commission
BEFORE INSERT OR UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
BEGIN
  IF :NEW.Salary > 50000 THEN
     :NEW.Commission := :NEW.Salary * 0.05;
  ELSE
     :NEW.Commission := 0;
  END IF;
END;
/

Statement-level audit row

Oracle PL/SQL · statement trigger
CREATE OR REPLACE TRIGGER log_employee_changes
AFTER INSERT OR UPDATE OR DELETE ON EMPLOYEE
BEGIN
  INSERT INTO AUDIT_LOG (Event_Time, Event_Type, Changed_By)
  VALUES (SYSDATE, 'EMPLOYEE CHANGE', USER);
END;
/
Trigger hazards

A trigger that queries its own table in a row-level trigger can raise Oracle's mutating table error. Cascading triggers can recurse; disable or guard them. Triggers are invisible side effects — document them, or a simple UPDATE may do more than expected.

Trigger vs constraint vs assertion

Constraint: declarative, local, fast. Assertion: declarative, schema-wide, not widely implemented. Trigger: procedural, can do anything, but harder to debug and port.

T-19

Privileges & authorisation

権限
5 M · lab

SQL's authorisation model gives users rights on objects. The DBA creates users and grants privileges; privileges can be revoked.

SQL · users and grants
-- create a user (Oracle)
CREATE USER dbms_user IDENTIFIED BY dbms123;

-- grant all privileges (lab requirement)
GRANT ALL PRIVILEGES TO dbms_user;

-- more controlled grants
GRANT SELECT, INSERT, UPDATE ON EMPLOYEE TO dbms_user;
GRANT SELECT ON PROJECT TO dbms_user;

-- allow the user to pass the privilege on
GRANT SELECT ON EMPLOYEE TO dbms_user WITH GRANT OPTION;

-- revoke
REVOKE INSERT ON EMPLOYEE FROM dbms_user;

-- roles group privileges
CREATE ROLE clerk;
GRANT SELECT, INSERT ON EMPLOYEE TO clerk;
GRANT clerk TO dbms_user;

Common privileges

  • SELECT — read rows; INSERT, UPDATE, DELETE — modify rows.
  • REFERENCES — create a foreign key referencing the table.
  • EXECUTE — run a procedure/function.
  • ALL PRIVILEGES — every privilege the grantor can grant on the object.
Oracle practical note

A newly created Oracle user usually also needs GRANT CONNECT, RESOURCE TO dbms_user; plus quota on a tablespace before it can log in and create tables. The exact lab steps depend on your institution's setup.

Security beyond GRANT

Views can restrict columns/rows; roles simplify administration; WITH GRANT OPTION delegates authority (carefully). Revoking a privilege can cascade to grants made by that user.

NULL & three-valued logic

NULLの扱い
5–7 M

NULL means “unknown, not applicable, or not available”. It is not zero and not an empty string, and it does not compare equal to anything — including itself.

Three-valued logic

Every predicate evaluates to TRUE, FALSE or UNKNOWN. WHERE keeps only rows where the predicate is TRUE; UNKNOWN is treated like false for filtering.

ExpressionResultCorrect test
NULL = NULLUNKNOWNcol IS NULL
NULL <> 5UNKNOWNcol IS NOT NULL AND col <> 5
Salary + NULLNULLCOALESCE(Salary,0) + …
NULL AND FALSEFALSE—
NULL OR TRUETRUE—
NOT NULLUNKNOWN—

Where NULL sneaks in

  • Aggregates ignore NULL — except COUNT(*). AVG(Salary) divides by the number of non-NULL salaries.
  • GROUP BY puts all NULLs into one group.
  • ORDER BY places NULLs first (Oracle default) or last (some systems); use NULLS FIRST/LAST where supported.
  • Outer joins manufacture NULLs for unmatched rows.
  • NOT IN (subquery) returns no rows if the subquery contains a NULL — use NOT EXISTS.
  • UNIQUE constraints usually allow multiple NULLs (Oracle), because two unknowns are not equal.

Handling NULL

SQL · NULL-safe expressions
SELECT Name FROM EMPLOYEE WHERE SuperSSN IS NULL;
SELECT Name FROM EMPLOYEE WHERE SuperSSN IS NOT NULL;

SELECT Name, COALESCE(Commission, 0) AS Commission
FROM EMPLOYEE;

SELECT Name, Salary + COALESCE(Commission, 0) AS Total_Pay
FROM EMPLOYEE;

SELECT COUNT(*) AS All_Rows,
       COUNT(SuperSSN) AS With_Supervisor,
       COUNT(*) - COUNT(SuperSSN) AS Without_Supervisor
FROM EMPLOYEE;
Classic exam trap

“Find employees who are not supervised” → WHERE SuperSSN IS NULL, not WHERE SuperSSN = NULL. The second predicate is UNKNOWN for every row and returns nothing.

Q1 · Database approach10 M

(a) Explain the main characteristics of the database approach. 3 + 7

Solution. The five core characteristics are:

  1. Self-describing nature: the catalog stores metadata (structures, types, constraints), so the DBMS can work with different applications.
  2. Insulation between programs and data: program–data independence; changing storage or structure does not require rewriting programs.
  3. Data abstraction: a data model hides storage details and gives a conceptual view; programs use model constructs.
  4. Support of multiple views: each user sees only the data of interest.
  5. Sharing and multi-user transaction processing: concurrency control keeps transactions correct; recovery makes completed transactions permanent. This enables OLTP with hundreds of concurrent transactions per second.

Q4 · Query processing10 M

Explain the steps in query processing with a diagram.

  1. User query input — SQL written at an interface.
  2. Parser — checks syntax/grammar, builds a parse tree; errors are returned for invalid syntax.
  3. Translator — converts SQL into an internal representation (relational algebra).
  4. Query optimiser — chooses the lowest-cost execution plan (e.g. index scan vs full table scan).
  5. Execution — runs the plan and interacts with storage.
  6. Storage manager — file manager (disk), buffer manager (memory), index manager (fast search).
  7. Database — actual tables/indexes; results return to the user.

Diagram (5 M): SQL → Parser → Translator → Optimiser → Execution → Storage Manager → Database. Label each box.

Q7 · Trigger10 M

Write a trigger to audit salary insert, update and delete on EMPLOYEE. Explain it. 6 + 4

CREATE OR REPLACE TRIGGER salary_audit
AFTER INSERT OR UPDATE OR DELETE ON EMPLOYEE
FOR EACH ROW
BEGIN
  IF INSERTING THEN
     DBMS_OUTPUT.PUT_LINE('New Salary: ' || :NEW.Salary);

  ELSIF UPDATING THEN
     DBMS_OUTPUT.PUT_LINE('Old Salary: ' || :OLD.Salary);
     DBMS_OUTPUT.PUT_LINE('New Salary: ' || :NEW.Salary);
     DBMS_OUTPUT.PUT_LINE('Difference: ' || (:NEW.Salary - :OLD.Salary));

  ELSIF DELETING THEN
     DBMS_OUTPUT.PUT_LINE('Deleted Salary: ' || :OLD.Salary);
  END IF;
END;
/

Explanation (4 M): row-level trigger → executes for each affected row. :OLD = value before, :NEW = value after. INSERT uses NEW; DELETE uses OLD; UPDATE uses both. The INSERTING/UPDATING/DELETING predicates select the event. AFTER timing means the change has already been applied.

Q8 · Assertion10 M

Write an assertion to ensure a manager's salary is greater than their employees' salaries. Explain it. 6 + 4

CREATE ASSERTION Manager_Salary_Check
CHECK (
  NOT EXISTS (
    SELECT *
    FROM EMPLOYEE E, DEPARTMENT D
    WHERE E.Dno = D.Dno
      AND D.MgrSSN = E.SuperSSN
      AND E.Salary >= (
        SELECT Salary FROM EMPLOYEE
        WHERE SSN = D.MgrSSN
      )
  )
);

Explanation (4 M): the inner query finds a violating pair — an employee in a department, supervised by its manager, earning at least the manager's salary. If no such pair exists, the assertion holds. It uses a correlated subquery and schema-level constraint enforcement.

Practical note: Oracle does not support CREATE ASSERTION; implement the same rule with a trigger. Mention this for extra credibility.
