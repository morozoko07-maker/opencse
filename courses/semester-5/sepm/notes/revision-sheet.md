# Revision sheet — Software Engineering and Project Management

The notes follow five modules: introduction and process models, requirements, design and implementation, testing, and project management. Questions usually give a scenario and ask you to choose a model or produce a diagram, so practise matching the clue to the answer.

## Exam pattern

The scheme papers show internal assessments of 40 marks in 1 hour 30 minutes, with four full questions to be answered. Each question is usually 5 + 5 or a single 10-mark part.

## Module 1 — Introduction and software processes

### Must know

- Software engineering covers all aspects of software production, not only coding: methods, tools, project management and quality.
- Essential attributes of good software: acceptability, dependability and security, efficiency, and maintainability.
- The four basic process activities: specification, development, validation and evolution.
- Waterfall is sequential: requirements, design, implementation, testing, deployment and maintenance. It suits stable, well-understood requirements.
- The spiral model is risk-driven. Each loop has four sectors: objective setting, risk assessment and reduction, development and validation, and planning.

### Definitions to reproduce

**Software engineering** — an engineering discipline concerned with all aspects of software production, from early concepts to maintenance.

**Software process** — a set of activities that leads to a software product.

**Spiral model** — an iterative, risk-driven process model in which each loop passes through objective setting, risk analysis, development and planning.

### Worked pattern

For a scenario, look for the keyword. Clear, stable requirements and a fixed deadline point to waterfall. Frequent changes and incremental delivery point to incremental development. High risk, prototyping or regulatory uncertainty point to spiral. Write the model name first, then justify it with two clues.

## Module 2 — Requirements engineering

### Must know

- User requirements are high-level statements for customers; system requirements are detailed and may form part of a contract.
- Functional requirements describe services; non-functional requirements describe constraints such as performance, security, usability and reliability.
- The requirements engineering process: elicitation and analysis, specification, validation and change management.
- Elicitation techniques: interviews, observation, scenarios, prototypes, focus groups and ethnography.

### Definitions to reproduce

**Requirement** — a statement of a service the system must provide or a constraint under which it must operate.

**Requirements elicitation** — the process of discovering requirements by communicating with stakeholders.

## Module 3 — Design and implementation

### Must know

- Design identifies components and their relationships; implementation realises the design as a program.
- Object-oriented design: define context, design the architecture, identify objects, develop models and specify interfaces.
- UML models: use case, class, sequence, state and subsystem diagrams.
- Design patterns are reusable solutions to recurring design problems. The Observer pattern decouples a subject from its observers; other common patterns include Composite, Facade, Adapter and Singleton.
- Implementation issues: reuse, configuration management, host–target development and version control.
- Open-source development publishes source code and invites contributions; it can reduce cost but raises support and licensing questions.

### Definitions to reproduce

**Design pattern** — a reusable description of a solution to a commonly occurring design problem.

**Configuration management** — the process of managing changes to a software system and its components.

## Module 4 — Software testing

### Must know

- Verification asks "are we building the product right?"; validation asks "are we building the right product?".
- Testing has two aims: demonstrate that the software meets its requirements and expose defects.
- Development testing: unit testing, integration testing and system testing.
- Test-driven development writes a test before the code, then refactors until the test passes. It drives design and gives regression tests.
- Release testing tests a complete release, usually as a black-box process; requirements-based testing is common.
- User testing: alpha testing in the developer's environment, beta testing with users, and acceptance testing against agreed criteria.
- Acceptance testing stages: define criteria, plan, derive tests, run tests, negotiate results, accept or reject.

### Definitions to reproduce

**Verification** — checking that the software meets its stated functional and non-functional requirements.

**Validation** — checking that the software does what the user actually needs.

## Module 5 — Project management and planning

### Must know

- Project management covers planning, risk management, people management, reporting and proposal writing.
- Risk types: project, product and business. The risk process is identification, analysis, planning and monitoring.
- Risk strategies: avoidance, minimisation and contingency planning.
- Managing people rests on consistency, respect, inclusion and honesty. Motivation comes from satisfying social, esteem and self-realisation needs.
- Software pricing depends on the contract type, estimate uncertainty, market conditions, requirements volatility and the reputation of the developer.

### Definitions to reproduce

**Risk management** — anticipating risks that could affect schedule or quality, then acting to avoid or reduce them.

**Project scheduling** — deciding how work will be organised into tasks, with durations, dependencies and resources.

**Plan-driven development** — development in which the process is planned in detail before implementation begins.

## Last 24 hours

- Match waterfall, incremental and spiral to three different scenarios.
- Write one functional and one non-functional requirement for a familiar system.
- Redraw the Observer pattern and the TDD cycle.
